# Key modules

Symposium is a Rust crate with both a library (`src/lib.rs`) and a binary (`src/bin/cargo-agents.rs`). The library re-exports all modules so that integration tests can access internals.

### `symposium-sdk`: the shared plugin vocabulary

Depended on by both Symposium and anything that extends it. Beyond the hook handler SDK, it carries what a package manager needs to speak:

- `manifest`: the unvalidated `Symposium.toml` schema (the `Raw*` types), `Serialize` as well as `Deserialize` so a manifest can travel on the wire. Retired fields (`crates`, `source.crate`, git/path chained sources) still *parse*, so validation can reject them with a migration hint rather than an unknown-field error. `MANIFEST_FILE` names the file a manifest is written in (`Symposium.toml`), shared by core's registry layout and the cargo PM.
- `pm`: `PackageId`, `PluginInfo`, and `UnvalidatedPlugin` (what a package manager answers with: Symposium validates it into a `Plugin`), and the `PackageManager` trait every package manager implements, re-exported from Symposium's `pm` module; plus `pm::protocol` (the wire format) and `pm::server` (the harness that puts a `PackageManager` on the wire as a PM binary).
- `predicate::syntax`: the predicate tree and its parsing.
- `hook::HookAgent`, `manifest::HookFormat`, `manifest::Audience`: named by manifests, so they travel with the schema. Mapping a `HookAgent` to its wire-format handler needs Symposium's agent modules, so that stays behind as `hook_schema::agent_event`.

What deliberately stays in Symposium is *validation*: defaults, inline-installation promotion, dormancy, trust. The schema says what a manifest can contain; Symposium decides what it means.

### `symposium-pm-cargo`: the cargo package manager

Its own crate, because it is its own binary. It holds everything specific to the cargo ecosystem: `CargoPm` (the PM), `workspace` (`WorkspaceDeps` / `WorkspaceCrate` / `LoadedWorkspace`: the `cargo metadata` call and its disk cache), `sources` + `probe` (`RustCrateFetch`: path override, workspace pin, registry, crates.io), `metadata` (the `[package.metadata.symposium]` table), and `manifest::merge` (layering that table with a `Symposium.toml`, leniently). It depends on `symposium-sdk` and nothing else of Symposium's, which is the check that the boundary is real, since it could not compile if it still needed policy.

It implements the SDK's `PackageManager` trait, the same trait every package manager implements, and runs two ways:

- **In-process**, the default: Symposium constructs it and calls the trait directly. The cargo PM is the one Symposium cannot do without, so it should not depend on finding a second binary, and the hook path should not pay a spawn.
- **Out-of-process**, as the `symposium-pm-cargo` binary: `pm::server::run` over the same type, constructed by `CargoPm::from_initialize` from the `initialize` handshake. The binary ships from the *main* crate (`src/bin/symposium-pm-cargo.rs`) so `cargo install symposium` installs it alongside `cargo-agents`; a PM the user has to install separately would be a PM that is usually missing.

`CargoPmConfig` (cache dir + cargo override) is what `WorkspaceDeps` needs from its host, built either from Symposium's `SymposiumDirs` or from the `initialize` handshake, so the resolver has no knowledge of Symposium's directory layout.

### `config.rs` — application context

Everything hangs off the `Symposium` struct, which wraps the parsed `Config` with resolved paths for config, cache, and log directories. Two constructors: `from_environment()` for production and `from_dir()` for tests. Agent relocation variables (`CLAUDE_CONFIG_DIR`, ...) are read through `env_dir`, which consults the process environment only for a `from_environment()` instance, so a test can never reach a developer's real agent directories; tests inject one with `set_env`.

Defines the user-wide `Config` (stored at `~/.symposium/config.toml`) with `[[agent]]` entries, logging, `[[registry]]` entries, defaults, `auto-update` (off/warn/on, default on), and the `[plugins]` enablement section. User config is deserialized through `RawConfig` and validated into the runtime `Config`; runtime code does not deserialize `Config` directly. A config that exists but cannot be read or parsed loads as the defaults with `auto-update` off and is recorded in `config_error`, so `save_config` refuses to write over it and `sync` refuses to run (see [configuration loading](./configuration-loading.md#config-loading)). `[[package-manager]]` entries (`PackageManagerConfig`: `name`, `command`, `args`) are the bootstrap channel for ecosystems Symposium does not know natively: each a binary speaking the PM protocol, spawned as a `RemotePm`. An entry named `cargo` *replaces* the built-in in-process instance rather than adding a second one, which is how even the cargo PM is run out of process. A configured PM is an ecosystem transport, so it is untrusted and its plugins are validated as packages: depending on an npm package should no more inject agent context than depending on a crate does. A spawned PM inherits Symposium's environment. `SYMPOSIUM_CARGO` is set explicitly, since the override lives in Symposium's directories rather than its process environment. Provides `registry_instances()` to build the effective registry `PmInstance`s directly (the builtin recommendations entry, the builtin `user-plugins` entry, then the configured ones): a git `[[registry]]` entry becomes a `GitPm`, a path entry a `PathPm`, each a trust root named for its registry (that name is what its plugins are attributed to). There is no `ResolvedRegistry`/`content_dir` intermediate: a git registry's cache directory and its refresh live on the `GitPm` itself. `Symposium::workspace(cwd)` is the one place an invocation's PM set is built: the ecosystem transports (the cargo transport over a `WorkspaceDeps` resolver for `cwd`, then any `[[package-manager]]`), then those registry instances, wrapped in a `Workspace`. `detached_managers()` is the workspace-independent form (registry listing, crates.io search): the cargo transport is built over a detached resolver that never runs `cargo metadata`, and a spawned PM is told there is no workspace. `workspace_deps(cwd)` builds the cargo resolver itself, wiring in `cargo_override` and `cache_dir` so it gets both the `SYMPOSIUM_CARGO` override and cross-invocation disk caching.

`PluginsConfig` (the `[plugins]` section) is the config surface of the [enablement axis](#discoveryrs--dependency-discovery-and-enablement): `auto-enable` (plugins pre-consented to; a bare `"*"` for all), `use` (`UseEntry::global` or `UseEntry::scoped` to a workspace: the durable record of a deliberate enablement), and `disable` (plugins pruned from enablement, which is also where a declined discovery is recorded). Every entry names a plugin as a `PluginRef`: a name, and optionally the PM that offers it, since two ecosystems may use the same word and what a name means is the offering PM's business. A bare name (`pm: None`) names whichever plugin of that name there is, and each list resolves one that could mean several by what the list is for: `use` through `discovery::Names` (below), `auto-enable` against the workspace's dependencies (`is_auto_enabled` covers nothing while two PMs' dependencies share the name), and `disable` not at all (`is_disabled` turns off every plugin of the name, the safe way to be wrong). Naming the PM is also what lets `disable` turn off one registry plugin. The query methods take a `PackageId` and the `Spellings` resolved for the workspace (`discovery::Names::spellings`): an entry names the id when it is spelled as the id is (`PluginRef::matches`), or when its package manager reads the entry as the same name as a dependency or registry plugin, so `widget-lib` names the dependency `widget_lib` while a registry's names compare exactly; `has_enablement_entries` is the cheap "could enablement pull in a crate plugin?" check the hook path uses to decide whether to resolve the crate graph. The lists are plain `Vec`s so a later `cargo agents use` can add and remove entries and call `save_config`.

### cargo workspace resolution (in [`symposium-pm-cargo`](#symposium-pm-cargo-the-cargo-package-manager))

The cargo-workspace resolution is **CargoPm's**, so it lives in the cargo PM's crate: `cargo metadata` is cargo's ecosystem, not a generic concern. `WorkspaceDeps` is the lazy, cached resolver for the cargo dependency graph: the first `load()` reads a disk cache keyed on `Cargo.lock` mtime, and on miss runs `cargo metadata` (extracting `root`, direct `crates`, and member dirs into a `LoadedWorkspace`) and writes through. The result is memoized in a `OnceLock`, so every accessor reads through a shared `&self` — which is what lets one resolver be shared as an `Arc`: a `CargoPm` holds one and *drives it* (`self.workspace.crates()` runs the metadata call). Core reads none of it: what Symposium learns about the cargo workspace comes through the PM's `list_deps` and `project_info` (its members as local packages, `Cargo.lock` and `battery-pack.toml` as inputs). `WorkspaceCrate` carries `path` (the local dir for a path dependency) and `source_dir` (the extracted source `cargo metadata` located, populated for registry crates too), so a workspace dependency's source is served without a fresh probe. `detached()` is a resolver pre-set to "no workspace" for workspace-independent operations (registry listing, search). The types re-export at `crate::pm` for convenience. The config-level `dirs.rs` (`SymposiumDirs`: config/cache paths + the `SYMPOSIUM_CARGO` override) stays in core; `Symposium::workspace_deps(cwd)` is the factory that turns it into the `CargoPmConfig` the resolver takes.

Members are recorded as `member_crates`, each a `WorkspaceCrate` whose `path` is the member's directory. They back workspace-plugin discovery and `crate-info` on a member, and stay out of `crates`, so a member never reaches `depends-on` or discovery as a dependency.

A failed `cargo metadata` is remembered with cargo's error and logged. `load()` reads it as no workspace, so hooks, help and the package-manager layer carry on without one; `require()`, used by `sync`, `status` and `use`, reports cargo's error, and keeps "not in a Rust workspace" for a directory with no `Cargo.toml` in it or above it.

### `agents.rs` — agent abstraction

Centralizes agent-specific knowledge: hook registration file paths, skill installation directories, and hook registration logic for each supported agent (Antigravity CLI, Claude Code, GitHub Copilot, Codex CLI, Kiro, OpenCode, Goose). Handles the differences between agents — e.g., Claude Code uses `.claude/skills/` and Kiro uses `.kiro/skills/`, while Antigravity, Copilot, Codex, OpenCode, and Goose use the vendor-neutral `.agents/skills/`. OpenCode and Goose are skills-only agents (no hook registration).


Hook and MCP registration is scope-dispatched: the project and global locations are genuinely different files for some agents (Antigravity writes `.agents/hooks.json` but `~/.gemini/config/hooks.json`; Copilot `.github/hooks/` but `~/.copilot/settings.json`), so `sync` calls the project-scoped functions at project scope rather than rooting the global path at the workspace.

MCP registration is its own axis, and the one place where guessing is expensive: an agent's MCP file is usually *not* its hooks file, so a wrong target fails **silently** - symposium reports success for a file the agent never reads. `Agent::mcp_config_path(scope, project_root, sym)` is the single seam holding that per-agent truth (the table lives in [agent details](./agent-details/README.md#mcp-server-configuration)), with `register_mcp_servers` / `unregister_mcp_servers` as the only entry points. Registration returns the names it wrote (leaving out servers an agent cannot take, like SSE on Codex), which `sync` and `init` record in the [MCP ledger](./state.md#mcp-server-ledger); unregistration takes the file from that ledger rather than a scope, and removes only what it lists. There is no separate project/global pair of functions to keep in sync. `McpScope` is deliberately distinct from `HookScope`: Antigravity, Claude, OpenCode and Kiro have a project-level MCP file, while Codex, the Copilot CLI and Goose read only a user-level one, so `supports_project_mcp_scope` reports when project scope is downgraded rather than writing a file nobody reads. Entry *shape* varies too - OpenCode needs `{type, command: [bin, ...args], enabled}` and rejects its whole config file otherwise, which is why it has its own serializer (`opencode_server_to_json`) instead of the shared `{command, args}` one.

Every JSON agent config goes through `save_json`, which replaces the file atomically (temp file plus rename, since Claude Code rewrites `~/.claude.json` mid-session). The rename would replace whatever the path names, so it resolves a symlink first and replaces the target, and gives the temp file the target's mode before writing: the file stays a link into the user's dotfiles, and a `0600` file holding tokens stays `0600`. A dangling link is an error and is left alone. The Codex and Goose files are edited in place, which keeps both without the rename. It also keeps the user's layout, so a committed config only shows the entry that changed: it reuses the file's indentation and ends it with a newline, and `serde_json` is built with `preserve_order` so keys stay in the user's order. Removing a key from a JSON config uses `shift_remove`, since `remove` would move the last key into its slot.

### `init.rs` — initialization command

Implements `cargo agents init`. Prompts for agents (or accepts `--add-agent`/`--remove-agent` flags), hook scope, auto-update behavior, and opt-in [telemetry](./telemetry.md); writes user config; and registers global hooks. Removing an agent re-runs `sync` in the current workspace, if any, so that agent's installed skills are reaped there.

### `sync.rs` — synchronization command

Implements `cargo agents sync`. Scans workspace dependencies, finds applicable skills from plugin sources, and synchronizes them into each configured agent's skill directory. The core primitive is `sync_skill_dir(source_dir, dest_dir, project_root)`. It copies the entire source directory (not just `SKILL.md`) and is change-aware: it compares source and destination content, only copying into a staging directory and swapping it in when files actually differ, so the disk shows no modifications when nothing changed and a failed copy leaves the installed one in place. Copying and comparing share one traversal, `walk_tree`: they have to agree entry for entry, since a comparison scan that omitted something the copier writes would see a difference on every run and turn each sync into a full recopy. That traversal **follows symlinks** (see [`dir_walk.rs`](#dir_walkrs--following-symlinks-without-looping)), so a linked file installs as a real file and a linked directory as its contents; a broken link and a link back into the tree being copied are reported and skipped rather than failing the sync. A configurable debounce (`sync-debounce-secs`, default 5s, keyed on the `.symposium` marker's mtime) skips even the comparison for recently-synced skills. On each sync, scans every agent's skills parent directory and reaps any marker-bearing subdirectory it didn't install this time, leaving user-managed skills (which lack the marker) and symlinks untouched; installed and scanned paths are compared resolved, so a skills directory linked to another agent's is not reaped through the link. Writes a `.gitignore` with `*` only into individual skill directories (not parent directories like `.claude/` or `.claude/skills/`). Also provides `register_hooks()` for use by `init`, which registers only symposium's own global hook handler; individual plugin hooks are never written into agent configs.

While `PluginRegistry::unreadable_registries` is not empty, `sync` skips that reap and warns once per registry: what an unreadable registry could not read offered nothing, so everything installed from it would look stale.

Installs, the reap, and agent config writes run under a blocking lock on `<cache>/sync.lock`, taken after resolution, so concurrent syncs (two agent sessions starting together) run one after the other instead of reaping each other's installs. See [sync concurrency](./sync-agent-flow.md#concurrency).

One entry point, `sync(sym, ws, update)`. The caller supplies the `Workspace`, so the hook pipeline hands over the PM set and workspace facts its other stages already resolved rather than resolving them a second time. Callers: the CLI's `sync` arm (after the consent prompt), `use_command` once an enablement is recorded, and the hook pipeline's auto-sync.

`sync` takes an `UpdateLevel` that it threads into skill resolution (`skills::collect_skills`), controlling how aggressively `source.git` skill groups are re-fetched. Callers choose: the auto-sync path passes `Check` on `SessionStart` (refresh) and `None` otherwise (debounced); the binary's global `--update` flag feeds manual `cargo agents sync`.

### `plugins.rs` — plugin registry

Loads plugin manifests from the configured registries and validates them into `Plugin`s. Loading goes through the [package-manager layer](#pm--package-managers): `load_registry` asks each **trusted** `PmRegistry` instance (the configured registries — the cargo transport is not a trust root) for its plugins via `active_plugins`. A `PathPm` returns each entry through `entry_plugin`: a `Symposium.toml` manifest read as-is, or a bare `SKILL.md` synthesized into a manifest (`standalone_skill_manifest`); dependency-embedded crate plugins never load here. Refreshing a git registry's content is the `GitPm`'s `refresh` operation, driven by `ensure_registries` (startup) and `sync_registries` (`plugin sync`). `scan_source_dir` remains as the offline form used by the `plugin validate` CLI, which points at an arbitrary directory rather than a configured registry; it walks the same [layout](#pm--package-managers) rules and synthesizes bare skills the same way.

`load_registry` reads each registry through `PmInstance::registry_plugins`, which returns `None` when the registry's `active_plugins` fails because the source cannot be read (a `PathPm` whose directory cannot be listed or is itself an entry, and a `GitPm` that has not been fetched). Such a registry is reported and recorded in `PluginRegistry::unreadable_registries` (see [common issues](./common-issues.md#a-source-that-reads-as-empty-is-not-an-empty-source)). The answer is a `PluginListing`, which also carries each entry that failed to load, so a registry with an entry that fails to parse or validate is recorded there too, while its other plugins still load. `plugin list` and `plugin show` read through the same call.

Validation here turns the raw TOML (parsed into the SDK's `RawPluginManifest`) into:
- `Installation` entries (optional `source`, optional `executable`/`script`, optional `args`, plus `requirements` and `install_commands`) collected on `PluginManifest.installations`. Inline installation references on hooks or other installations are *promoted* into synthetic `Installation` entries with derived names (`<hook>` for an inline `command`, `<owner>__req_<i>` for an inline requirement), so all references in the validated form are plain names.
- `Hook` entries with `command: String` (the name of an `Installation`) plus optional hook-level `executable` / `script` / `args`. Validation guarantees at most one of `executable`/`script` is set across hook + installation, and at most one layer sets `args`.
- `SkillGroup` and `PluginMcpServer` entries whose `depends-on` sugar and `predicates` list are merged into one runtime `PredicateSet`. Skill group `source` syntax is deserialized as raw string/table forms, then validated into `PluginSource`.
- `ChainedPlugin` entries from `[[plugins]]`: a per-edge `PredicateSet` plus a `source.cargo` reference (dependency-atom string `"widget>=1"` or `{ name, version }` table) naming the crate that carries the referenced plugin. This is the "package ≡ plugin" edge — how one plugin (e.g. a recommendations manifest) names another plugin by its package. Validation rejects git/path sources and the retired dependency-table form with hints. Expansion is wired in `skills.rs`: when the owning plugin is active and the edge predicates hold, the referenced crate is loaded (see [important flows](./important-flows.md#crate-sourced-skill-resolution)) — as a first-class plugin from its own `Symposium.toml` if it ships one, otherwise from the crate's metadata / default-`skills/` path. The recorded version requirement is not yet enforced at resolution — the crate resolves against the workspace.

The cargo PM's `manifest::merge(metadata, file, crate_name)` builds a crate's unvalidated manifest. It parses each source (the `[package.metadata.symposium]` table and a `Symposium.toml` file, both in the ordinary plugin-manifest schema) independently and **leniently** (a malformed layer is logged and dropped), merges them (`RawPluginManifest::merge`: list fields append, scalar/keyed fields take the later layer, gates AND together). When the plugin reaches `validate_plugin`, the result runs through the same `validate_manifest` pipeline under `ManifestOrigin::Crate`: the `name` defaults to the crate, the dormancy rule does not apply (the reference that reached the crate is the gate), `[defaults]` is accepted, and the default `skills/` group is appended (but not the workspace-only `.agents/skills` group). A crate with neither source still yields that default group. `Plugin` carries a required `canonical: PackageId`: the resolved crate id for a crate-sourced plugin, or a placeholder id tagged with the source name (registry) / `"local"` (workspace) for plugins with no real package identity. It keys chained-plugin cycle/diamond detection on its package identity (`PmRegistry::identity`); it does *not* affect skill identity, which is the `SKILL.md` path hash (see `skills.rs`). Every loader (`load_plugin_as`, `workspace_plugin_for_dir`, and `validate_plugin`) runs `resolve_group_sources` before returning, so each `[[skills]] source.path` group carries an **absolute** directory plus a display `source_label`, and a `Plugin` needs no base/manifest dir. A `Plugin` carries no manifest file path or base path at all: its identity is its `canonical` id. `plugin show` renders a plugin's effective config keyed by that id (not a re-read manifest file); `plugin validate` reports each item by its id/name (a failed load's error message still carries the file it came from).

There is no separate "standalone skill" concept: a registry directory holding only a `SKILL.md` (no `Symposium.toml`) is synthesized by `standalone_skill_manifest` into a manifest with default values, which ordinary registry validation turns into a plugin — named for the skill's own frontmatter `name` (falling back to the directory), carrying a single `source.path = "."` skill group that rediscovers that `SKILL.md`, and with the skill's frontmatter `depends-on`/`predicates` **hoisted to the plugin gate** so the ordinary dormancy rule applies (a bare skill that names no dependency is dormant until `use`d). This mirrors how a crate with no manifest still yields a plugin with the default `skills/` group. So `PluginRegistry` holds only `plugins`; the `plugin validate` CLI likewise reports a bare skill as its synthesized plugin, whose one child is the skill. Returns a `PluginRegistry` — a table of contents that doesn't load skill content.

A registry manifest that references no dependency anywhere (plugin, `[[skills]]`, `[[hooks]]`, `[[mcp_servers]]`, or `[[plugins]]` chain edge, via `depends-on`, a `depends-on(...)` predicate, or a custom predicate) is not an error: it validates and loads with `PluginManifest::requires_use = true`, i.e. *dormant*. `Plugin::applies` short-circuits to false for a dormant plugin unless `PredicateContext::is_used` lists its canonical id, so every activation path (skills, hooks, MCP, subcommands, help) agrees. That list comes from `discovery::used_plugins`: the plugins an applicable `[plugins] use` entry names, each by its manifest name under its own package manager's rule, so `use = ["my-plugin"]` wakes a registry plugin `my-plugin` and `use = ["my_plugin"]` does not. `depends-on = ["*"]` remains the explicit always-active spelling, and `plugin validate` reports dormancy as a warning. So a recommendations-registry entry, an ordinary flat plugin, stays out of dormancy by declaring its own `depends-on` (the crates it advises, or `["*"]`). The positional origins never go dormant, because where they were found supplies the gate.

Workspace-scoped callers use `load_registry_with_workspace`, which additionally loads *workspace plugins* (`workspace_plugins`): the workspace root and every member the package managers report inside it (`Workspace::info`) each define a plugin when they carry a `Symposium.toml` (validated with `ManifestOrigin::WorkspaceMember` — `name` defaults to the directory name, membership is the gate so dormancy never applies, and the default groups are appended unless `[defaults] skills = false`: `[[skills]] source.path = "skills"` plus, when the `agents-syncing` config is on, a `workspace-member()`-gated `[[skills]] source.path = ".agents/skills"` — the maintainer-skills convention, unified into the ordinary pipeline) or a bare `skills/` or `.agents/skills/` directory (an all-defaults manifest-less plugin). Workspace plugins are stamped `workspace_member = true` — the producer of the `workspace-member()` predicate — and attributed to the `"(workspace)"` source with skill paths relative to the workspace root.

### `dir_walk.rs` — following symlinks without looping

The two rules every source-tree walk needs once symlinks are followed, in one place.

It lives in `symposium-sdk` (`symposium_sdk::dir_walk`, re-exported in core as `crate::dir_walk`): the cargo PM's crate walks package content too, and depends on the SDK alone. Any package manager scanning a source tree needs the same guard.

A live source tree — a workspace member, a path or git dependency, a `[[registry]]` path entry, `~/.symposium/plugins/`, a git-cloned registry cache — can contain symlinks, and what sits behind them is skill content like any other. Such a tree is *dereferenced* rather than copied link-for-link: the destination is a different tree, so a preserved relative link pointing outside the skill directory would dangle there. Dereferencing also makes a source-tree install agree with a crates.io install, which already delivers real files (`cargo package` follows links, including ones escaping the package root). Links are followed wherever they point — there is no containment check against the source root; the [skill reference](../reference/skill-definition.md#symlinks-in-skill-content) records that decision and its rationale.

- `resolved_kind(path, file_type)` classifies a directory entry with links resolved. `DirEntry::file_type` reports the *link*, which is neither a directory nor a regular file, and `DirEntry::metadata` does not follow it either; `fs::metadata` does. `Err` can only come from that follow, so it means a broken link.
- `Ancestors` records the directories a walk is currently inside, by canonical path, and refuses to enter one twice. A tree of real directories cannot contain itself, so this only fires once a directory link has been followed — but every directory on the way down is recorded, since the link that closes the loop may sit several real directories below the one it names.

Four walks use it: the copy/compare traversal in [`sync.rs`](#syncrs--synchronization-command) (both rules), and the cycle guard alone in skill discovery (`skills::find_skill_files_recursive`), registry enumeration (`pm::layout::walk`), and crate content detection (`contains_skill_md` in `symposium-pm-cargo`) — those three already followed directory links through `Path::is_dir`.

### `installation.rs` — sources and acquisition

Defines `Source` (the `source = "..."`-tagged enum: `cargo`, `github`) and `acquire_source`, which downloads / installs / clones the source and returns an `AcquiredSource` whose `resolve_executable` / `resolve_script` methods turn a relative `executable`/`script` name into a concrete path. The `Runnable` enum (`Exec(PathBuf)` or `Script(PathBuf)`) is the final form a hook command resolves to. The `git` submodule handles GitHub tarball acquisition and caching.

`acquire_source` (and the main-crate `acquire_installation` wrapper) take an `UpdateLevel`. `None` serves the cache without touching the network; `Check`/`Fetch` re-resolve. Hook dispatch acquires with `None`; the `SessionStart` prewarm uses `Check`. The three source kinds:

- **crates.io cargo**: the resolved version is recorded in a `current` pointer (`<cache>/binaries/<crate>/current`). `None` reads the pointer and serves that version with **no crates.io query** — so a per-event dispatch never hits the registry. `Check`/`Fetch` query for the newest matching version, install into its version-keyed dir, and rewrite the pointer (so newly published versions are picked up at session start, not on every event). Only `Fetch` forces a same-version reinstall.
- **`cargo + git`**: the cache key folds in only the URL + user version, never the resolved commit, so a moved branch never invalidates it on its own. `Check`/`Fetch` resolve the remote `HEAD` with a cheap `git ls-remote` and compare against the commit recorded in a `.commit-sha` file in the cache dir; the binary is reinstalled (`cargo install --force`) **only when the SHA changed** (or `Fetch`, or the binary is missing). `None` never resolves the remote.
- **github** (script/subtree sources): honors the level directly via the git cache manager (freshness checks debounced to a 60s window under `None`).

Validates skill group source constraints during manifest validation: a group must set exactly one of `source.path` or `source.git` — a missing `source` (or an empty `source = {}`) is rejected, as are both together. A crate is not a skill-group source — `source = "crate"` (and the legacy `source.crate` table) is rejected with a hint to use a `[[plugins]] source.cargo` chained reference instead.

### `pm/` — package managers

A dependency listing containing IDs owned by another package manager is incomplete: core drops those IDs and records the offering PM as failed, preserving cleanup safety while retaining valid dependencies from the other PMs.

The seam from the [registry-centric plugin distribution RFD](../rfds/registry-centric-plugins/README.md). An instance may run **in-process** (`PathPm`, `GitPm`, `CargoPm`) or as a **separate binary** (`RemotePm`, speaking newline-delimited JSON-RPC over stdio; see [`pm/remote.rs`](#pmremoters-out-of-process-package-managers) below). Both implement the same trait, so nothing above `pm/` knows which it is talking to. A `PackageId` is the canonical `(pm, name, version)` tuple; `version` may still be a requirement (a semver range, or `*` for "no requirement"), and `fetch` canonicalizes it — a `FetchedPackage` carries the exact resolved id plus the content directory. A `PluginInfo` (id plus optional description) is the lightweight result of `search`.

The `PackageManager` trait is the RFD's operation set, defined once in the SDK (`symposium_sdk::pm`) and re-exported here: the same trait a PM author implements, whether Symposium will run it in-process or spawn it. Plugin loading has two forms, `active_plugins(deps)` (the plugins a PM activates for the workspace deps, as a `PluginListing` that also carries the entries it could not read) and `load_plugin(id, update)` (the plugin(s) a specific id maps to, served only from disk under `UpdateLevel::None`), both returning `UnvalidatedPlugin`s; plus `list_deps`, `project_info` (the project the PM finds from the starting directory: its root, its local packages, and the files whose change means its answers may have changed), `search`, `fetch`, and `refresh` (pull a registry's content; a no-op default for local/dependency sources). Every operation returns a `Result`. `PmInstance` turns a failure into an empty answer for its caller *and* records it (`PmInstance::has_failed`, collected by `PmRegistry::failed` and `Workspace::failed`), so a failure never reads as "nothing here" to the code that removes what is no longer offered. `load_plugin` is the exception: it is a question about one package, so a package that cannot be loaded is logged and contributes nothing, rather than stopping cleanup for its whole ecosystem. The git-vs-path descriptor `plugin list` shows is `PmInstance::source`, set by the config that built the instance rather than asked of the PM. A PM value is an *instance*, not just an ecosystem: a **transport** can `fetch`/`load_plugin` any id of its ecosystem because the id carries the source, while a **registry instance** fronts one configured source and enumerates its packages via `active_plugins`. A registry instance's `name()` is the *configured registry name* (`user-plugins`, `symposium-recommendations`, …), which is also the `pm` component of every id it mints and the name its plugins are attributed to. A PM is *self-contained*: it holds whatever it needs to resolve its own ecosystem, so operations take no ambient context — mirroring the out-of-process shape, where a PM spawned for a workspace answers from its own state. `CargoPm` holds an `Arc<WorkspaceDeps>` and drives it (lazy, cached); `PathPm` holds its directory. `PmRegistry` is **one flat set** of instances: `fetch` / `load_plugin` dispatch by `PackageId::pm`, and `list_deps` / `search` union across all, an instance that fails contributing nothing. An answer carrying an id that names a different PM than the instance that gave it is dropped (a plugin, a dependency, a search hit) or refused (a fetch), since ids route by that component and consent and `disable` are keyed on it. So is a relative path, which would resolve against wherever Symposium happens to run: in a `project_info` (the instance's answer fails), a plugin's `root` or `label_root` (the plugin is dropped), or a fetched package's root (the fetch fails). An `UnvalidatedPlugin` is the resolved `id`, the content `root`, and an **unvalidated** `RawPluginManifest` (plus an optional `label_root`, the directory resolved skill paths are *displayed* relative to, so a registry entry reads as `path:<entry>/skills`). The manifest is the point: a PM may have parsed it from a `Symposium.toml`, translated another ecosystem's manifest, or synthesized one for a package that describes itself not at all, and Symposium cannot tell.

Whether two names are the same package is the PM's rule too: `canonical_name` gives the form in which two of its package names compare equal. `CargoPm` folds `-` into `_`, as cargo does; a registry (`PathPm`, and `GitPm` through it) keeps the default and compares names exactly. It is an operation like the others, asynchronous and fallible (`PmInstance::canonical_name` falls back to the name as written and records the failure), so it is asked only about a name someone typed: a PM spells each of its packages one way in every answer, so ids compare as they are, and `PmRegistry::identity` only drops the version. `PmInstance::find` says whether a PM has a package of a name someone typed. It is built from the operations every PM has, so no PM implements it and the protocol has no request for it: a dependency of that name (`list_deps`), otherwise a package already on disk (a cache-only `fetch`; for `CargoPm`, a crate in cargo's extracted sources, `probe::find_cached`), and, above `UpdateLevel::None`, otherwise one its `search` turns up. A registry's packages are the plugins it lists, which its caller already holds, so a trusted instance has none to find. The level follows the same split as crate loading: hook dispatch, `--help`, subcommand dispatch and `status` pass `None`, so they never search crates.io or spawn cargo, while `use`, `use --remove` and `sync` pass `Check`, which reads the cargo cache first and searches only for a crate that is not cached. A name no PM has is never a crate assumed to exist.

Turning an `UnvalidatedPlugin` into a `Plugin` is `PmInstance`'s job, via `plugins::validate_plugin`: schema validation, inline-installation promotion, default content, dormancy, and resolving `source.path` groups against the plugin's root all happen there. Each `PmInstance` carries two flags, both Symposium's to set and neither anything a PM says about itself:

- `trusted`: whether consent is needed. Registries and the workspace are trust roots; the ecosystem transports (cargo and any `[[package-manager]]`, over dependencies) are not. This is the distinction consumers branch on (registry loading takes only trusted instances; `discover` takes only the untrusted transports).
- `kind: PluginKind`: which validation policy applies. `Registry` (must name itself, `[defaults]` rejected, [dormant](#pluginsrs--plugin-registry) with no gate) or `Package` (id supplies the name, the reference that reached it supplies the gate, default `skills/` group appended).

So a package manager cannot make itself trusted or wake a dormant plugin by what it returns. A package's manifest can still turn off the default `skills/` group with `[defaults] skills = false`, since that is part of the package schema. A registry plugin that fails validation is reported, naming its directory, since fixing it is the user's job; a package's failure is only logged, since it is its author's, and a report on the hook path would land next to the agent's JSON. `Symposium::workspace(cwd)` builds the set: the cargo instance (`trusted = false`, in-process unless a `[[package-manager]]` entry named `cargo` displaces it), then any other configured `[[package-manager]]` (`trusted = false`, spawned), then one registry instance per configured registry (`trusted = true`: a `GitPm` for a git entry, a `PathPm` for a path entry). Names are what ids route by and `[plugins]` entries are keyed on, so a `[[package-manager]]` name must be a plain identifier no other package manager or registry has, or the config is rejected at load (`RawConfig::check_package_manager_names`). `detached_managers()` uses a detached resolver for workspace-independent work. `Workspace::dep_ids()` is the union of every instance's `list_deps`, resolved once per invocation. `CargoPm` ([`symposium-pm-cargo`](#symposium-pm-cargo-the-cargo-package-manager), in-process by default): `fetch` delegates to `sources::RustCrateFetch` (path override, workspace pin, registry); `list_deps` reads `self.workspace.crates()` as cargo ids, failing (rather than answering empty) when a `Cargo.toml` is present but `cargo metadata` failed; `active_plugins(deps)` returns (via the shared `plugin_from_fetched`) each dependency whose source embeds plugin content (a `Symposium.toml`, `[package.metadata.symposium]`, or the default `skills/`), served from the source `cargo metadata` already extracted (no probe); these are dependency-embedded, so the caller applies consent; `load_plugin(id)` returns the named crate whatever it embeds (any fetchable crate yields at least a default `skills/` plugin), fetching a crate outside the workspace through cargo the first time and from cargo's cache after that; `search` queries crates.io (`crates_io_api`, capped at `SEARCH_PAGE_SIZE`) so `use`/`search` can name a crate the workspace doesn't depend on. `CargoPm` also owns crate-to-plugin resolution:
- `plugin_from_fetched(fetched) -> UnvalidatedPlugin` builds the unvalidated plugin for a fetched crate from its manifest sources (`[package.metadata.symposium]` in `Cargo.toml` and a `Symposium.toml` at the source root) layered by `manifest::merge` (see [important flows](./important-flows.md#crate-sourced-skill-resolution)). The plugin's id is the resolved crate. A crate with **no** manifest sources still yields one carrying an empty manifest, which validation turns into a plugin whose only content is the default `skills/` group, so `load_plugin` returns a plugin for any fetchable crate (a failed fetch is an error, recorded against the instance). The default group is appended by validation, not by the PM: defaults are policy.

`Workspace` is the per-invocation handle threaded above `pm/`: the PM set plus the two facts about the workspace everything needs, both the package managers' answers, each resolved once and cached. `info()` is where the workspace is: the project the package managers find from the starting directory (for a hook, the payload's `cwd`, see [hook flow](./hook-flow.md)), as root, members and inputs. Where a project is rooted is each ecosystem's own rule, so only a package manager can say; every one that finds a project must report the same root, and a disagreement is an error (`require_info`) rather than a choice. Members outside the root are dropped, since their plugins would be trusted. `dep_ids()` (from `list_deps`) is what it depends on. A package manager that fails to answer is recorded (`failed()`): its silence is not an empty answer, so sync skips its cleanup. `reuse` takes the workspace and dependencies recorded at the last sync instead of asking, which is how a hook event with nothing changed avoids asking (or spawning) any package manager. `Symposium::workspace(cwd)` is the single construction point, so one invocation shares one PM set; that matters little when every PM is in-process and rebuilding the set is nearly free, and a great deal when one is a subprocess and rebuilding means respawning.

A package manager that fails to describe the project is left out, and the others decide where the workspace is. Failing the workspace instead would let one broken package manager (a missing binary, a `Cargo.toml` mid-edit) stop syncing for every ecosystem. The cost is accepted knowingly. Had the failed one answered, it might have disagreed about the root, which is an error; while it is down, skills install where the others put the root, and because its failure skips cleanup, they stay there once it recovers and the disagreement stops syncing. That needs a failure and a disagreement at once, and it leaves extra skills behind rather than removing wanted ones. The sync is still recorded, so the failed package manager is asked again at the next `SessionStart`, a manual `sync`, or a change to another input, rather than on every event, where a hung one would cost its timeout each time.

Callers stay ignorant of crates: `skills.rs` hands over a dependency name and gets back a parsed plugin. Consumers: chained-reference expansion in `skills.rs` calls `load_plugin`; `crate_command.rs` builds ids with `CargoPm::id_for` and fetches through `PmRegistry`; every dependency-list site (hook dispatch, sync, help rendering, subcommand dispatch, skill matching) gets its `PredicateContext` deps from `Workspace::dep_ids`. Sync helpers that used to take `&[WorkspaceCrate]` and resolve deps themselves (`help_render::render`, `subcommand_dispatch::find_subcommand`) now take an already-resolved `&[PackageId]`, so only the async entry points touch the PM layer.

One registry-instance PM exists today, reading content that is already on disk:

- **`pm/layout.rs`** — the packaging convention it reads: `classify(dir)` (a directory with a `Symposium.toml` is a plugin entry, one with a `SKILL.md` is a bare-skill entry — loaded as a default plugin — manifest wins) and `enumerate(root)` (recursive walk that does not descend into a claimed directory, sorted, erroring when the root is itself an entry). The layout carries no dependency information — an entry declares which dependencies activate it through its own manifest `depends-on`. Interpreting an entry's manifest stays in `plugins.rs`.
- **`pm/path.rs` — `PathPm`** — one local directory in the flat layout: `~/.symposium/plugins/`, a `[[registry]]` `path` entry, or the git cache directory a git registry unpacks into (serving as a `GitPm`'s inner reader). Its ids name the entry's subpath within the source. `active_plugins` returns every entry (via `plugins::entry_plugin`), `load_plugin(id)` the entry an id names, `fetch` joins the subpath back onto the directory, and `search` substring-matches entry names. Its `source()` is the `Path` descriptor its instance carries. A registry is a trust root, so its plugins activate without consent; entry-load failures surface as report warnings.
- **`pm/git.rs` — `GitPm`** — one `[[registry]]` `git` entry. Once fetched, a git repo is just a directory, so the reads (`active_plugins` / `load_plugin` / `search` / `fetch`) delegate to an inner `PathPm` over the cache directory; the git-specific part is `refresh`, which pulls the repository (Symposium skips it for an entry whose `auto-update` is off unless the user names it), and its `source()` is the `Git` descriptor. Its `active_plugins` fails until the repository has been fetched, so an unfetched registry is unreadable rather than empty. The builtin `symposium-recommendations` repo is such a registry (an ordinary flat registry — each entry names the crates it advises with its own `depends-on`, so no namespacing or dedicated convention is involved).

#### `pm/remote.rs`: out-of-process package managers

`RemotePm` implements `PackageManager` by spawning a PM binary and speaking the SDK's protocol to it over stdio. Two properties it exists to hold:

- **Lazy spawn.** The process starts on the first operation that needs it, not at construction, so a configured PM that nothing asks about costs nothing. On the hook path, an event whose package-manager inputs are unchanged since the last sync asks no PM where the workspace is or what it depends on, so no PM is spawned unless a package it owns has to be loaded; and when one is asked, the cargo PM's `Cargo.lock`-keyed disk cache lives inside it, so it holds either side of the boundary. A spawn is not free, which is why the cargo PM runs in-process by default.
- **Degrade, never abort.** Failing to spawn, failing the handshake, dying mid-request, timing out (30s per request unless `timeout-secs` says otherwise), or answering with garbage all fail the operation, which `PmInstance` records and turns into an empty answer: one broken PM never breaks a sync or a hook, and its silence is never mistaken for an empty answer. A PM that failed this way is killed and marked unavailable rather than respawned per call, and a dropped connection kills its process too (`kill_on_drop`), so a PM stuck mid-answer never outlives the invocation. A request is taken out of the connection while it is in flight, so one abandoned midway (its future dropped) leaves the PM unavailable rather than a connection whose next read is the abandoned answer. An error *response* is different: it is the PM answering, so the call fails and the connection stays up. One plugin in an answer that does not decode is dropped on its own.

`RemotePm` asks the PM's `canonical_name` as a request and keeps each answer for the connection, so a name costs one round trip. A name mismatch at handshake is a hard failure, not a warning: ids route by their `pm` component, so a PM answering to a different name than it was registered under would silently misroute every id. Protocol-version negotiation is strict for the same reason.

The wire format and the server harness live in the SDK, since a PM author needs them: `symposium_sdk::pm::protocol` (JSON-RPC 2.0, newline-delimited, `initialize` / `active_plugins` / `load_plugin` / `list_deps` / `project_info` / `search` / `fetch` / `refresh`, one request at a time) and `symposium_sdk::pm::server` (implement the trait, call `run` with a factory that builds the PM from the `initialize` parameters). `initialize` carries the per-invocation context (workspace, cache dir) so no later method takes ambient context. A configured PM gets a cache directory of its own (`<cache>/pm/<name>`); with a long-lived process the workspace is fixed for the connection, which is why `list_deps` has no parameters. A PM's stderr is logged at debug level rather than passed through, since on the hook path Symposium's own stderr reaches the agent. `tests/remote_pm.rs` drives real subprocesses, including the failure modes.

### crate metadata (in [`symposium-pm-cargo`](#symposium-pm-cargo-the-cargo-package-manager))

`metadata.rs` extracts the `[package.metadata.symposium]` table from a crate `Cargo.toml` and returns it verbatim as a `toml::Table`. That table uses the **same schema as a `Symposium.toml` plugin manifest** — a crate can define its plugin inline in `Cargo.toml` instead of (or in addition to) shipping a file. `manifest::merge` deserializes the table and merges it with any `Symposium.toml`; validation happens later, on the other side of the PM boundary, when the resulting plugin reaches `plugins::validate_plugin`. There is no longer a separate crate-metadata skill schema: the old `path = "..."` / `crate = {..}` redirect forms are now ordinary `[[skills]] source.path` groups and `[[plugins]] source.cargo` chained references.

### `predicate.rs`: predicate evaluation

The predicate *syntax* (the `Predicate` tree, both surface spellings, parsing, `Display`, and serde) lives in `symposium_sdk::predicate::syntax` and is re-exported here, so `crate::predicate::Predicate` still names the same type. The split lets a manifest carry predicates without linking evaluation. Evaluation is the `PredicateEval` extension trait, an extension trait because the types are foreign.

The syntax covers both dependency-graph matching and runtime/environment gating: one `Predicate` enum, `PredicateSet` (a list ANDed together), and this module's `PredicateContext` (the workspace dependency list it evaluates against, `PackageId`s from the [package-manager layer](#pm--package-managers)'s `list_deps`, plus the `use` entries that wake dormant plugins, resolved by `discovery::used` before they are threaded in with `with_used`, and read by `is_used`). Two surface syntaxes lower to the same tree:

- The **`depends-on`** field uses dependency-atom syntax (`serde`, `serde>=1.0`, `npm:react`, `*`; a `Dependency` of optional PM, name and version requirement) and lowers, via `DependsOnList`, to `depends-on(...)` / `depends-on(*)` predicates OR-combined into a single `any(...)` that is appended to the same list. So `depends-on` is sugar — there is no separate dependency-predicate type.
- The **`predicates`** field uses function-call syntax: `depends-on(<atom>)`, `shell(<cmd>)` (verbatim arg, `sh -c`, exit 0 holds), `path_exists(<arg>)` (disk, then `$PATH` for bare names), `env(<name>[=<value>])`, `workspace-member()` (the plugin is defined by a member of the active workspace — provenance stamped per plugin into `PredicateContext` via `Plugin::applies`; registry loading stamps false, workspace-plugin loading stamps true), and the combinators `not(<p>)`, `any(<p>, …)`, `all(<p>, …)`. The retired `crate(...)` spelling is rejected with a migration hint, as are the old `crates` fields.

Each gated struct (plugin, skill group, skill, hook, MCP server, subcommand) stores a single merged `predicates: PredicateSet`. Evaluation is `PredicateSet::evaluate(ctx) -> bool` — a predicate is purely a boolean gate. A `depends-on` atom matches a dependency by exact name, from the PM it names or, naming none, from any; a version requirement is checked when the dependency id's version component parses as semver. `collect_dep_names` (crates.io validation) walks all positions regardless. Plugin/group/skill/MCP predicates are evaluated at sync time; hook dispatch evaluates the plugin-level set (so a plugin's `depends-on` now gates its hooks) plus the hook-level set. Hook dispatch threads in the workspace crate list, but resolves it (running cargo) only when some plugin- or hook-level predicate references a *concrete* `depends-on(...)`, or there is crate-plugin expansion to perform — a chained `[[plugins]]` edge or a `[plugins]` enablement entry (`hook_dispatch_needs_deps`) — since expansion evaluates predicates against the crate graph too. A workspace whose plugins have none of these dispatches without a cargo query. See the [predicates reference](../reference/predicates.md).

### `skills.rs` — skill resolution and matching

Given a `PluginRegistry` and workspace dependencies, this module resolves skill group sources, discovers `SKILL.md` files, and evaluates dependency predicates at each level (plugin, group, skill) to determine which skills apply. It resolves skills over `plugins::active_plugins`, the crate-expansion walk that produces the shared active plugin set every facet resolves over (see below), so the same set that resolves skills also feeds MCP-server, hook, and subcommand dispatch. Every `source` funnels through one seam: `resolve_group_dirs` turns a group into a list of `ResolvedSkillDir` (a base directory + report labels), then `collect_skills_from_dirs` scans each base for `SKILL.md` files. `PluginSource` has exactly two variants — `Path` (already on disk, relative to the plugin's source dir) and `Git` (fetched via the git cache); a source is required, so there is no "no source" state.

The single seam every facet resolves over is `active_plugins`: it returns the full active set: every registry plugin whose gate holds (cloned), followed by the crate-sourced plugins transitively reached through `[[plugins]]` chained references and dependency enablement. Skills, MCP servers, hooks, and subcommands all iterate this one list, so a crate-sourced plugin's extensions dispatch exactly like a registry plugin's. Crate loading takes an `UpdateLevel`: on the per-invocation paths (`--help`, subcommand dispatch, hook dispatch) it is `None`, under which `CargoPm` reads a crate that is not a workspace dependency only from cargo's extracted sources, so building the set never spawns cargo on the per-event hook path. `sync` passes `Check` and `crate-info` fetches with `Check`, so those two download a crate that is not cached yet.

`active_plugins` is a **worklist fixed-point over the PM set** (`pms`). It seeds the active set with the trust-root plugins the registry loaded (`registry.plugins`, each gated by `record_active`), then works a queue of `PackageId`s: each active plugin's `[[plugins]]` chained `source.cargo` references (edges whose predicates hold, evaluated against the owning plugin's provenance) plus the consented enabled-dependency ids (below). For each id it calls `pms.load_plugin(id)`, dispatched to the owning PM (the cargo transport builds the crate as a first-class `Plugin` from `[package.metadata.symposium]` + `Symposium.toml` + defaults), gates each result, records it, and enqueues *its* own edges. A `visited` set keyed on the package identity (`PmRegistry::identity`: the id as its PM spells the package, version dropped) collapses diamonds (a crate reached two ways loads once, so its hooks don't double-fire and its subcommands aren't a false conflict) and breaks cycles; the finite crate universe bounds termination, so there is no depth cap. `collect_skills` then walks the active set and runs each plugin's skill groups through the ordinary `load_skills_for_group` pipeline; each discovered skill's install identity is the hash of its on-disk `SKILL.md` path (below), so a crate reached two ways dedupes to one install. A crate plugin's **custom predicate definitions** are the one facet not yet wired in: `warn_undispatched_crate_features` logs when a crate declares one.

The enabled-dependency ids seed the same worklist: `discovery::enabled_dependencies` returns the package ids, of any package manager, covered by `[plugins] auto-enable` or an applicable `use` entry (both the workspace deps it enables *and* the `use`d packages that aren't deps at all), and each is pushed as it is, so a package's `skills/` (or manifest) installs with no plugin manifest anywhere pointing at it. The `use` entries arrive resolved by `discovery::Names`, so a bare name that wakes a dormant registry plugin is not also loaded as a crate of that name. This is where consent lands: `enabled_dependencies` reads the `[plugins]` config, so only consented crates enter the worklist.

Production `sync` shares one `PredicateContext` across the skill and MCP passes, so it calls `active_plugins` then `collect_skills` directly rather than the `skills_applicable_to` convenience wrapper (which builds its own context and is test-only).

Each applicable skill carries an **origin hash** (a `String`) describing *where its bytes live*, used at sync time for dedup and install-path disambiguation. `skill_origin_hash` computes it as an 8-hex-char prefix of SHA-256 over the `SKILL.md`'s **canonical** on-disk path — nothing else. Identity is the file's location, not which plugin manifest pointed at it: two references that resolve to the same file (the same crate reached through two chained plugins, or two `source.path` groups landing on the same bundle) produce the same hash and dedupe; skills at different paths stay distinct. Canonicalizing inside the hash is what makes that hold across discovery paths, since group scan dirs are canonicalized inconsistently — so on a platform whose temp prefix is a symlink (macOS `/var` → `/private/var`) the same file would otherwise hash two ways and install twice.

Because the hash is the dedup key itself, a 32-bit collision between two genuinely distinct paths would silently drop one skill (rather than clashing loudly at install time) — a deliberate trade for carrying only a string, not a structured origin, to the sync layer.

`sync` prefers the plain `<agent-skills-dir>/<skill-name>/` and only falls back to `<skill-name>-<origin-hash>/` when needed: when more than one origin claims the same skill name, or when the unsuffixed slot is already occupied by a user-managed directory (one without the `.symposium` marker). The suffix is an 8-hex SHA-256 prefix for every origin kind. The `.symposium` marker, wildcard `.gitignore`, and stale-cleanup walk all key on the marker file rather than directory name shape, so transitions between unsuffixed and suffixed names self-heal across syncs.

The skill name comes from plugin content and becomes that directory name, so it is untrusted input: `load_skill` rejects any name `is_safe_dir_name` refuses (one that could resolve outside the skills directory), and the skill fails to load instead of being installed. `Agent::project_skill_dir` and `global_skill_dir` assert the same check before joining the name.

### `discovery.rs` — dependency discovery and enablement

Enablement is the second axis alongside activation predicates: predicates say *when* a plugin applies, enablement says *whether it may run at all*. The workspace and the configured registries are trust roots; a dependency deliberately is not, since depending on a crate should not let its author inject agent context. So a plugin embedded in a dependency runs only with consent, and a registry plugin with no gate to infer stays [dormant](#pluginsrs--plugin-registry) until named. The two trust roots are loaded and gated directly (registry plugins by `load_registry` + `Plugin::applies`, workspace plugins the same way), so they never reach discovery. What `discover` classifies is exactly the untrusted offers: the dependency-embedded plugins an ecosystem transport (`CargoPm`, or a `[[package-manager]]`) surfaces. The trust boundary is the instance's `trusted` flag, which Symposium sets: a registry's plugins are loaded directly, while a transport's are the consent path's concern.

A bare `use` name is resolved by `Names`, built from the loaded registry, the workspace's dependencies and the PM set: the nearest of a registry plugin (dormant or not, so a bare name that woke one never falls through to a crate of that name once it gains a gate) or a dependency answers, and matches from two PMs there leave it ambiguous. A bare name neither has is left `unknown` for `enabled_dependencies`. `used(sym, root, names)` resolves the applicable entries into a `Used`: the qualified `PluginRef`s every predicate context and `enabled_dependencies` take, the unknown ones, and the ambiguous ones, which enable nothing and which `sync` and `status` report. `Names::spellings` resolves the `auto-enable` and `disable` entries the same way, into the `Spellings` the `PluginsConfig` queries take: each entry with the dependencies and registry plugins its package manager reads as the same name but spelled differently. A package loaded after that (a chained crate, a `use`d one) is added as it loads (`Names::spell`), from a package manager that was just asked for it. Both ask a package manager only about a name not spelled as it reports the package, so a workspace whose entries are spelled as written costs no request. `used_plugins` is the form the call sites building a context use, and `discover_for` resolves them itself for callers holding no registry. What Symposium writes is always precise, naming the package manager; bare names are for entries the user writes.

`discover(sym, ws, used)` takes the workspace root from the handle (nothing to discover outside a workspace) and asks the **untrusted** instances (the ecosystem transports) for their `active_plugins(dep_ids)`: the plugins embedded in the workspace's dependencies (for cargo, read from the sources `cargo metadata` already extracted, no probe). Each is classified by `decide` against `[plugins]` on its own id, so consent is per package manager: `Used`, `Declined`, `AutoEnabled`, or `Candidate`, and lands in the matching field of the returned `Discovery` (`active` / `auto_enabled` / `candidates` / `declined`). Explicit decisions outrank standing ones, so a declined name stays declined. Discovery writes nothing; the trusted registries are skipped, since their plugins are trust roots and never need consent.

`enabled_dependencies(sym, pms, dep_ids, used, update)` is the activation side, consumed by `plugins::active_plugins` and `status_command.rs`: the package ids to load, from any package manager: workspace deps that `auto-enable` or an applicable `use` entry enables, plus `use`d packages that aren't deps at all (so `cargo agents use <crate>` pulls a plugin from crates.io whether or not you depend on it), minus the disabled ones. A `use` entry counts only when it names an untrusted instance in `pms`; one naming a registry wakes that registry's dormant plugin in place. A bare name `Names` left `unknown` is looked for in each ecosystem package manager (`PmInstance::find`) at `update`: found by exactly one, it is that package; by several, it is ambiguous and enables nothing; by none, it is skipped (and `status` lists it as dormant). Under `None` that includes a crate cargo has not cached yet, which the next `sync` downloads. `auto-enable` contributes only deps: it is consent for what a dependency carries, not a way to add crates.

On top of that read side sits the consent write side. `prompt_for_consent(sym, deps, out)` asks one question per candidate (enable / ask me later / never ask again) and `apply_consent` records the answers precisely, under the id of the package manager that offered each plugin: approvals into `auto-enable`, declines into `disable`, saved to the user config. Only explicit answers are recorded: the default ("ask me later") and Escape write nothing, so reflexively hitting Enter never permanently declines anything.

**The prompt is inert unless `out.is_interactive()`** — a non-quiet, non-capturing `Output` attached to a terminal on *both* ends. That is the whole safety property: hook dispatch and anything an agent triggers run with a quiet output, and the library test harness runs with a capturing one, so neither can reach stdin. A bare TTY check would not do, since `cargo test` inherits the developer's terminal. The only caller is the `Commands::Sync` arm in `cli.rs` — the hook-triggered auto-sync path calls `sync::sync` directly and never passes through it. `pending` is the non-interactive counterpart: `hook.rs`'s `consent_hint` renders it into `SessionStart` context so the agent can tell the user, without symposium ever blocking.

### `use_command.rs` / `search_command.rs` / `status_command.rs` — the enablement commands

The user-facing surface over `discovery` and `[plugins]`.

`use_command` records enablement. `use_plugin` resolves the name in three tiers, and the first with a match answers: registry plugins that name themselves, then workspace dependencies (both through `Names::nearest`, so the command and a bare config entry agree), then `PmRegistry::search` over the ecosystem transports. Within a tier, matches are deduplicated on `(pm, normalized name)`; `--pm` narrows every tier. Exactly one match is used; several is an error listing them, resolved with `--pm`; none is refused with `no package named ...`, and nothing is written. A match named in `[plugins] disable` is refused, since `disable` outranks every way of enabling; re-enabling is dropping that entry. A trust root's plugin needs no entry, with a dormant one the exception, since `use` is how it wakes. The recorded `UseEntry` names the chosen plugin precisely, `(pm, canonical-name)`, so it round-trips to the same plugin in every workspace. Both it and `remove_plugin` re-run `sync::sync` afterward, so skills install or are reaped immediately. `remove_plugin` matches on scope, and on `--pm` when given (a bare entry by the PM it resolves to), and errors when nothing matched rather than silently succeeding. Wherever a plugin is shown to the user to enable (the consent prompt, the `SessionStart` consent hint, a `status` candidate), it is shown as `pm:name`, and `discovery::use_command` gives the `use` command with `--pm`.

`search_command` unions two arms: plugin names in the loaded `PluginRegistry` (bare skills included, since they are now plugins) and `PmRegistry::search` across every instance (which matches registry entry subpaths, e.g. a skill's directory name). A PM without a searchable registry returns an empty list and a failing instance is skipped, so an offline registry degrades the results instead of failing the command. Hits are grouped by originating instance for display; the `SearchMatch` report event carries the origin for the JSON form. A second-arm hit with the same origin and name as a first-arm one is dropped.

`status_command` renders the enablement report. `workspace_status` walks the registry plugins (root: workspace membership, `use`, or the registry name; state from `Plugin::applies` plus the `requires_use` gate), which is where every recommendations-registry plugin appears, then every `Discovery` bucket of dependency-embedded plugins (`Used` / `AutoEnabled` -> active with that root, `Candidate` -> awaiting consent, `Declined`), then the `use`d crates that aren't dependency offers (from `enabled_dependencies`, e.g. `use`-ing a crate the workspace doesn't depend on, otherwise invisible to discovery; a workspace dependency there offers no plugin, so it is shown only when a `use` entry names it, as dormant), then, as dormant, any `use` name no package manager has at `UpdateLevel::None`, then any `[plugins] disable` name discovery never saw. Status resolves names at `None`, so it never searches crates.io. The four `StatusState` values (`Active`, `Dormant`, `Candidate`, `Declined`) are the report's vocabulary.

### `subcommand_dispatch.rs` — plugin-vended subcommands

Routes the `Commands::External` arm of clap's `allow_external_subcommands`. `dispatch_external` first resolves the active plugin set (`plugins::active_plugins`), so crate-sourced subcommands dispatch too; `find_subcommand` walks that set, applying plugin-level and subcommand-level dependency predicates against the workspace (with the applicable `use` names, so a dormant plugin's subcommands appear once it is enabled), and returns the matched `(Plugin, Subcommand)` (or an error if more than one plugin claims the name). `dispatch_external` then looks up the named `Installation`, resolves it via `installation::resolve_runnable`, and spawns the child with stdio inherited — propagating the exit code as a `u8` so callers can convert to `ExitCode` (binary) or treat non-zero as an error (library). `applicable_subcommands` is the shared iterator over the active set's applicable subcommands, taking an already-resolved `&[Plugin]` so help rendering and the `SessionStart` discovery hint reuse it.

### `help_render.rs` — `--help` rendering

Renders `cargo agents --help` as two audience-grouped sections, "Commands for humans" and "Commands for agents", mixing built-in subcommands with plugin-vended ones filtered by the active workspace. Built-in audience comes from `cli::builtin_audience`; plugin subcommands come from `subcommand_dispatch::applicable_subcommands` over the resolved active plugin set (`plugins::active_plugins`), so crate-sourced subcommands appear in help too.

`help_text` is the single help decision, shared by the binary and the test harness. clap's own help flag and help subcommand are disabled (in `cli::Cli`), `--help`/`-h` is a manual `global` bool, and the entry points parse with `try_parse_from` — so help is decided *after* parsing and argument order (`--help --quiet`) is irrelevant. It returns the top-level grouped help for no subcommand / `--help` / `-h` / the bare `help` keyword; for `<built-in> --help` it re-renders clap's own per-command help by walking clap's command tree (so required-arg commands like `crate-info`, required-subcommand groups like `plugin`, and nested commands like `plugin list` all work); a plugin `<name> --help` returns `None` so dispatch forwards `--help` to the child.

`render` builds the grouped text by slicing clap's rendered help — keeping the header (before `Commands:`) and the options block (from `Options:` on) and hand-rendering only the two section headings between them. If a slice marker is missing (clap format drift), it falls back to clap's unmodified help rather than panicking.

### `hook.rs` — hook handling

Handles the hook pipeline: parse agent wire-format input → auto-sync → builtin dispatch → plugin hook dispatch → respond. The response is a `HookResponse` (stdout, stderr, exit code), since some decisions travel only through the exit code: a plugin hook's exit 2 on `PreToolUse` becomes a canonical deny (`blocked_response`), and Kiro receives any denial as exit 2. A single `Workspace`, found from the payload's `cwd` (the process's working directory when the payload has none), is threaded through all stages: `run_auto_sync`, `dispatch_builtin`, `dispatch_plugin_hooks`, and the `SessionStart` prewarm. So each package manager is asked each question at most once per hook call, and an out-of-process PM is spawned at most once. Across invocations, per-directory state (`workspace_state.rs`, keyed on that directory, since knowing the root would mean asking) records the workspace the last sync found and its inputs' modification times; while none of those files has changed, an event asks no package manager where the workspace is or what it depends on, the common case for `PreToolUse` hooks. A workspace that names no inputs is never fresh. Loading a package a plugin chains to, or one `use` enables, still asks its package manager.

`run_auto_sync` takes a `session_start` flag: on `SessionStart` it skips the freshness gate and syncs with `UpdateLevel::Check` (so upstream skill/source changes land once per session); every other event keeps the gated, `UpdateLevel::None` path. The matching `ensure_registries` refresh level is decided in the binary entry point from the same event. `SessionStart` additionally runs `prewarm_hook_sources` (best-effort, gated by `auto-sync`): it walks every applicable plugin's hooks and *refreshes* each installation's already-cached source via `refresh_installation_if_present` (`UpdateLevel::Check`). This is what keeps hook *binaries/scripts* (not just manifests) current once per session — in particular the only path that re-pulls a `cargo + git` hook binary whose branch moved — so the dispatch path can keep acquiring with `None` (cache/debounced) and pay no per-event network cost. It is **refresh-only**: a source that was never acquired is left alone (it installs lazily on first dispatch), so `SessionStart` never eagerly installs a tool a hook may never use.

On `SessionStart`, `handle_session_start` composes three independently-computed `additionalContext` fragments: a `discovery_hint` (suggests `cargo agents --help` when the workspace exposes applicable plugin subcommands, reusing `subcommand_dispatch::applicable_subcommands`), a `consent_hint` (names the dependency plugins awaiting consent, via `discovery::pending` — a hook must never block on stdin, so the candidates are reported as context pointing at `cargo agents sync` / `cargo agents use` rather than asked about), and an `update_nudge` (the throttled self-update warning); only the nudge is gated behind the update-check throttle. `handle_post_tool_use` and `handle_user_prompt_submit` add one generic notice (there may be new plugins, run `cargo agents sync`) when `run_auto_sync` reports that it re-synced because `Cargo.lock` changed. The plugin dispatch path matches plugin `Hook`s against the event over the active plugin set (`plugins::active_plugins`, so crate-sourced hooks fire too), selects the best format for each plugin (native match > symposium > single-other-agent fallback), builds a `ResolvedHook` per match (looking up the named installations on the plugin, adding the command's and each requirement's own requirements one level deep, and taking the installation's `args` when the hook sets none), then for each `ResolvedHook`: acquires its `requirements` (best-effort), runs `install_commands` after the source step, picks a `Runnable` from (hook-or-install) `executable`/`script`, and spawns it (binary directly for `Exec`, via `sh <path>` for `Script`). Input is delivered in the selected format; output is converted back to the agent's wire format before returning.

### `state.rs` — persistent state

Manages `state.toml` in the config directory. Deserializes through `RawState` and validates into the runtime `State`. Tracks the semver of the binary that last touched the directory (for future migration hooks) the timestamp of the last update check (to throttle crates.io queries to once per 24 hours), and the [MCP server ledger](./state.md#mcp-server-ledger): the `(agent, file, name)` of every MCP entry symposium wrote, so removal never touches an entry the user wrote under the same name. `ensure_current()` is called on startup to silently stamp the current version. `should_check_for_update()` / `record_update_check()` gate the auto-update flow.

### `telemetry/` — opt-in usage telemetry

Implements the local, opt-in [telemetry](./telemetry.md) event log under `<config-dir>/telemetry/`, one JSONL file per UTC day. Off by default; gated by `[telemetry] enabled`. A `TelemetryEvent` is an `at` timestamp plus a kind-tagged `EventKind` (`session_start` / `user_prompt` / `tool_use`), serialized one per line. `record` / `record_kind` append an event; `roll_off` deletes files older than `RETENTION_DAYS` (30); `read_events` / `recent_events` read them back; `usage` + `status_text` back `telemetry status`; `recent_events` backs `telemetry show`. Events are anonymous by construction — no prompt text, command lines, or file paths. Every write path is best-effort — failures are logged and swallowed so a hook is never broken. The recording entry points are not yet called from the hook pipeline, so no events are produced today even when telemetry is enabled.

The replacement recording contract is being built behind private `schema`, `identity`, and `state` submodules before it is connected to production callers. Within `schema`, `mod.rs` owns shared row primitives and version dispatch, `macros.rs` owns strict versioned-row boilerplate for rows with and without cross-field validation while each row module keeps its validation rules, `metrics.rs` owns the fixed latency histogram and complete-session validation shared by hook aggregate rows, and `hook.rs` owns the strict hook-metrics row and read-side validation. Its `hook/surface.rs`, `hook/outcome.rs`, `hook/key.rs`, and `hook/update.rs` children keep SDK surface mapping, outcome accounting, the typed `hook_subject` dimension and aggregate key, and atomic write updates with their respective tests. `plugin_hook.rs` owns the strict plugin-hook aggregate row and read-side validation. Its `plugin_hook/outcome.rs`, `plugin_hook/bucket.rs`, and `plugin_hook/update.rs` children keep outcome accounting, validated public identity and pre-admission attribution, and atomic write updates with their respective tests. `name.rs` owns validation shared by public name types, `agent.rs` owns agent vocabulary and agent-originated rows, `command.rs` owns eligible built-in and public plugin-command coordinates and exhaustively maps parsed CLI commands into the recorded built-in set, `extension.rs` owns validated public extension coordinates and vocabulary shared across event kinds, and `resolution.rs` owns resolution summaries and shared resolution vocabulary. Package-resolution vocabulary and validated public coordinates live in `resolution/package.rs`; `resolution/extension.rs` owns the strict recursive node vocabulary, the validated path wrapper that enforces whole-path depth, leaf-count, and encoded-size limits, the skill-only attribution persisted by the installation index, and the versioned row that derives `extension_subject` from its target and path. Timestamped rows validate during deserialization that `day` is the UTC calendar day containing `at`; the later archive reader separately validates that the row belongs to its daily file. Private state binds its key and identifier-window or return-cohort anchor into distinct identity scopes. Each identifier domain accepts only its contract-selected scope. Row constructors take a bound recording context, derive identifiers from their own source fields, and take their day from the context: package resolution derives `package_subject` from its coordinate, agent configuration derives `agent_subject` from its agent, command derives `command_subject` from its coordinate, and a full resolution reuses one context for its summary, package, and extension rows. Session start extends that context with a return-cohort scope and derives its timestamp, both subjects, and `cohort_day` from one bound session transition. Within `state`, `mod.rs` owns the versioned private-state file shape, `state/lifecycle.rs` owns the identifier-window transition for every recording plus return-cohort and identifier-reset transitions, `state/open_day.rs` centralizes the monotonic day transition used by daily state while persistence remains responsible for sourcing it from the one latest-opened-day high-water mark, `state/session_pair.rs` owns the bounded two-set storage and permanent-incompleteness rule shared by aggregate trackers, `state/session_counts.rs` owns hook-specific contribution classification and count reconciliation, `state/hook.rs` owns the deterministic daily map that selects those trackers by aggregate key, and `state/plugin_hook.rs` keeps each plugin-hook row's admitted identity, stable event ID, and session tracker behind one key-checked selection. Its `state/plugin_hook/admission.rs` child owns the deterministic daily map and the separate 128-public-row allowance for this aggregate family. Only this private-state boundary can create an overflow bucket; row constructors receive the coupled identity from the selected entry rather than accepting its scope, coordinate, and subject separately. A completed recording transition is a single-use value; a session transition extends it with the return-cohort selection. Binding either transition against unchanged anchors exposes only the identity scopes valid for that operation. Each hook row and private tracker share a key made from the UTC day and `hook_subject`, so equally sized trackers for different aggregates cannot be exchanged. Hook-metrics updates derive their row and session identities from one bound recording, reject impossible per-observation plugin counts, stage every row counter before changing private session state, and publish the two objects only after every checked update succeeds. The private `storage` submodule owns the new contract's canonical paths and exclusive filesystem access: `StoragePaths` keeps inspectable data and its permanent `.lock` under `<config-dir>/telemetry/` while keeping `telemetry-state.toml` beside that directory, and `TelemetryLock` makes one non-blocking acquisition whose file handle releases the lock on drop or unwind. The eventual recorder will stage rows and aggregate changes in memory, successfully replace the private state containing their anchors and entries, and only then expose those rows for publication. Their tests remain beside the responsibility they exercise.

Hook, plugin-hook, and extension-invocation aggregate keys retain their
validated source dimensions. Each key can therefore be rebuilt from a stored
identifier-window scope without trusting persisted subject bytes.

`storage/metrics/recovery.rs` indexes every surviving public row for allowance
reconciliation separately from subject-matched rows that private state may
adopt. Duplicate matches choose the lowest `event_id` deterministically.

`state/staged_entries.rs` provides a per-entry copy-on-write overlay for
aggregate maps. The hook store applies day rollover and tracker edits through
that overlay. Plugin-hook and extension-invocation admission also stage their
open day, public-row spend, and every recovered or newly admitted entry.
Dropping a stage leaves its real store unchanged, while a selection error
poisons the stage so commit discards all of its edits. `state/aggregate.rs`
owns the three stores as disjoint fields and exposes the borrow seam that lets
the recording coordinator keep all three stages live together.
`state/aggregate/recording.rs` owns the complete invocation input, derives its
plugin totals, and returns an unpublished staged snapshot. Its `stages.rs`
child opens all three private stages, checks the snapshot day, applies one
staged unit, and performs the shared poison preflight; `rows.rs` selects and
mutates each family's row against the owned snapshot; and `error.rs` keeps the
content-free failure vocabulary.

`state/aggregate/persistence.rs` wraps the three family wire shapes and owns
cross-family row-identifier uniqueness plus agreement between every store day
and the identity high-water day. Its `sessions.rs` child is the private wire
bridge for the shared session pair. It preserves permanent incompleteness,
rejects malformed or oversized raw sets, and checks the family-specific subset
and contribution relationships without giving runtime trackers general-purpose
serialization.
Its `hook.rs` sibling defines the strict borrowed and owned hook-store wire
shapes, re-derives hook subjects from the document's identity scope, and runs
the same store validator before encoding and after reconstruction.
`plugin_hook.rs` adds the plugin-hook row identifier, strict public, unnamed,
and overflow bucket shapes, and persisted public-row spend. It re-derives
public plugin subjects from the document scope and rejects duplicate keys,
row identifiers, inconsistent spend, and mismatched entry identity.
`extension_invocation.rs` persists the analogous extension store while keeping
each public bucket's validated skill target and complete safe resolution path
together. It revalidates recursive paths during decoding and re-derives both
agent and extension subjects from the document scope instead of trusting
stored subjects.

`state/codec.rs` owns canonical private-state serialization, version dispatch,
schema decoding, and secret-safe diagnostics. It is the only bridge between
the runtime state and the strict aggregate wire adapters, so aggregate
invariant failures remain typed without giving identity-bearing runtime types
general-purpose serialization. `state/lifecycle.rs` advances all three
aggregate-store days before mutating identity state on every accepted
operation. Day rollover clears entries and resets public-row spend, while an
identifier-window rollover or identifier reset clears entries and preserves
same-day spend. The private `storage` module owns the bounded file I/O that
calls the codec.

Resolution summaries derive an optional `session_id` from a paired agent and
raw vendor session identifier rather than accepting a loose scoped identifier.
`state/codec.rs` owns canonical private-state encoding and content-free decode
errors, so malformed state can never expose the identity key in diagnostics.

`schema/extension_invocation.rs` is the extension-invocation aggregate boundary. Its `extension_invocation/vocabulary.rs` child keeps the closed version 1 agent, phase, target-scope, and unnamed-reason vocabulary; `extension_invocation/bucket.rs` accepts only safe public attribution or a fixed unnamed reason, leaving overflow assignment to private state; and `extension_invocation/row.rs` owns the strict versioned row and its read-side scope, counter, and session validation. The row's `update.rs` child applies one phase observation atomically from a bound recording and an admitted private-state selection, so the event id, agent, target identity, identifier epoch, and session tracker cannot be supplied independently. The independent attempted/completed session-count validator lives with the other aggregate primitives in `schema/metrics.rs`. `state/extension_invocation.rs` owns phase-specific contribution counts and reconciles them with the stored row over the shared bounded session pair. Failed observations add no session id, but still perform this reconciliation so a lost snapshot row cannot leave published counts inconsistent with private state. Its `extension_invocation/admission.rs` child derives coupled row identity, keeps the stable row identifier and session tracker behind one epoch-aware aggregate key, and sends new public targets beyond the daily allowance to overflow. `state/public_row_budget.rs` owns the shared 128-row daily allowance used independently by each named aggregate family: day rollover and clear restore it, while identifier reset does not.

Storage acquisition also tightens a pre-existing telemetry directory and lock
file to owner-only modes on Unix instead of relying only on their creation
modes. `storage/atomic.rs` writes a complete byte buffer through a
same-directory temporary file before atomically replacing its destination; it
does not fsync, and callers must finish serialization before replacement. Every
telemetry-owned temporary uses the shared `.telemetry-tmp-` prefix so lazy
cleanup and status recognize the same namespace. Activating the replacement
recorder must remove the legacy `record` and `roll_off` paths in the same
change, so two schemas and retention policies never share the telemetry
directory.

`LockedStorage` owns both the canonical paths and `TelemetryLock`, so private
state cannot be loaded or replaced outside the lock. Its `private_state.rs`
child performs a bounded byte read, distinguishes TOML syntax errors, invalid
state content, and unsupported versions without retaining parser source text,
serializes the complete state before replacement, and requires mutable access
to replace it. Its `daily_files.rs` sibling recognizes only canonical event
and metric filenames. Its `events.rs` sibling validates one-day low-volume
batches, serializes every row before filesystem access, and appends them in one
write after closing any partial final line left by an earlier failure.
`storage/limits.rs` measures the two daily files, performs a bounded final-line
inspection, reserves the largest version 1 storage-limit marker, and makes the
all-or-marker decision with saturating arithmetic. Inspection or marker-
preparation failure suppresses only the current event append, while a stored
or surviving final marker closes low-volume recording for that UTC day without
stopping aggregates. Its `metrics.rs` sibling loads the 512 KiB aggregate
snapshot as one fail-closed unit, retains each validated row's original
physical bytes, exposes event-id-only insert and replace operations, sorts
prepared rows by canonical wire labels, and atomically replaces only a fully
prepared snapshot that fits both storage ceilings. Unsafe snapshot content
stops aggregate updates for that day without stopping event appends. When
private state is absent, storage initializes the high-water mark and
identifier-window anchor from the later of the current UTC
day and the newest surviving daily filename; malformed and unsupported state
remain errors rather than entering this path.

### `report.rs` — structured report layer

Provides user-facing output for all commands via a custom tracing layer. Commands emit `tracing::info!` or `tracing::debug!` events with a `report = %ReportEvent::Variant { ... }` field; the `ReportLayer` intercepts these and renders them based on mode:

- `Normal` — prints `format_human()` to stdout (default for most commands)
- `Verbose` (`-v`) — prints all events (info + debug) to stderr
- `Json` (`--json`) — accumulates events in a buffer, drained as a JSON array at the end

The `ReportEvent` enum is the stable schema — `#[derive(Serialize, Deserialize)]` with `#[serde(tag = "kind")]`. Each variant carries the fields needed to render both human and JSON forms. The `Display` impl serializes to JSON (for passing through tracing's `%` formatter), and `format_human()` renders the pretty-printed form.

The layer is always installed by the binary. Commands that want output simply emit report events at the appropriate tracing level (info for actions, debug for decision trace). The `--json` flag also suppresses the `Output`-based messages and drains the JSON buffer at exit.

### `self_update.rs` — self-update

Implements `cargo agents self-update`. Queries the registry for the latest published version via `cargo search`, then installs it via `cargo install symposium --force`. Also provides `re_exec()` which replaces the current process with the newly installed binary (Unix `exec`, spawn-and-exit on Windows) — used by the `auto-update = "on"` startup path. Contains `maybe_warn_for_update()` (sync, for the `warn` library path) and `maybe_check_for_update()` (async, for the binary `on` + re-exec path).

### `crate_command.rs` — crate source lookup

Contains `dispatch_crate()`, which resolves a crate's version and fetches its source code. Called by the CLI's `crate-info` command. Path dependencies are resolved to their local source directory via `WorkspaceCrate.path`. Without `--version`, a workspace member is looked up in `member_crates` first and resolves to its own directory.
