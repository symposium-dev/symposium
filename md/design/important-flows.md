# Important flows

This section describes the logic of each `cargo agents` command.

## Crate-sourced skill resolution

A plugin loads a crate as a plugin by naming that crate in a `[[plugins]]` chained reference (`source.cargo = "..."`); the user can also load one directly by enabling the dependency it lives in (see [enablement](#dependency-enablement) below). When the owning plugin is active and the edge's predicates hold, the crate is resolved into the **active plugin set** — the shared list every facet (skills, MCP servers, hooks, subcommands) resolves over, so a crate-sourced plugin's extensions dispatch exactly like a registry plugin's. A single path handles every crate — a crate is always a first-class plugin, whether it describes itself with a `Symposium.toml`, with `[package.metadata.symposium]`, with both, or with neither:

1. The active-plugin fixed point seeds a worklist from the trust-root plugins the registry loaded. Ordinary callers use its boolean adapter; sync uses its optional-witness adapter. Both evaluate the same branches once. Each active plugin's `plugin.chained` edges whose predicates hold (evaluated against the *owning* plugin's provenance) contribute a `source.cargo` crate id.
2. For each request the fixed-point calls the owning package manager. An enabled dependency enters the worklist as its admitted handle, so equal coordinates with different supplier keys remain distinct. A new `[[plugins]]` edge or a non-dependency named by `use` enters as an unresolved coordinate. Core sends the former back to its supplier as `PackageLoadTarget::Resolved` and the latter as `Coordinate`; it never reconstructs an exact request by looking up a coordinate. A hook that reused durable dependency coordinates refreshes and admits that supplier's current dependency snapshot before creating exact requests, because keys are never persisted.
   - `CargoPm::fetch` resolves the source via `RustCrateFetch`. A workspace dependency is served from the source `cargo metadata` already extracted. Any other crate is read under `UpdateLevel::None` from cargo's extracted registry sources with no process or network, and goes through the Cargo probe under `Check` or `Fetch`. Every route produces the same `PackageResolution`: an exact coordinate, a payload-free source classification, and Cargo's opaque package identity as the session key.
   - `CargoPm::plugin_from_fetched` returns that resolution with the crate as an unvalidated plugin. Its manifest layers `[package.metadata.symposium]` from `Cargo.toml` and `Symposium.toml`; malformed layers are logged and dropped.
   - A crate with neither source but a `plugin.json` at its root is an Agent Plugins package instead. The cargo PM only flags it (`UnvalidatedPlugin::agent_plugin`): the translator lives in Symposium, and its warnings belong in the user's report, which a package manager running as its own process cannot reach.
   - The cargo instance validates it (`plugins::validate_plugin` with `PluginKind::Package`). A flagged package is first translated by `plugins::agent_plugin_manifest` into one skill group per immediate child of `skills/` and its `mcp.json` into MCP servers, with the default `skills/` group turned off. The translation is strict, so an invalid `plugin.json` makes the crate yield no plugin at all (reported as a warning) rather than falling back to its `skills/` folder. For any other package, a `plugin.json` beside its manifest sources only fills the `name`, `version` and `description` they leave out; a malformed one is logged.
   - The core Cargo instance admits the resolution with built-in authority, then validates it under `ManifestOrigin::Crate`. The result retains the resolved coordinate plus a private admitted package carrying session identity, classification, and core authority. A configured replacement PM named `cargo` uses the same wire shape but receives remote authority. A crate with no manifest sources and no `plugin.json` still yields a plugin whose only content is the default `skills/` group.
3. Before gating, `plugins::withheld` asks the [audits list](../reference/audits.md) (the builtin `symposium-audits` list, read from its git cache) whether this release or payload is revoked (`AuditIndex::revocation`); a revoked plugin is dropped, with a debug report and a log line naming the reason, and its edges are not followed. This is the single activation check, and every route (chained references, `auto-enable`, `use`) passes through it.
4. The traversal honors the plugin-level predicates once, appends the plugin to the active set, and **enqueues its own `[[plugins]]` edges**. With telemetry consent, that same pass retains safe route evidence, exact contributor handles, and each successful package-to-package edge in a private in-memory graph; without consent it retains none of the three. A terminal map keyed on `(PackageHandle, validated plugin name)` collapses diamonds and breaks cycles without conflating supplier resolutions that share a coordinate. An identity enters the map only after revocation or a passing gate, so a predicate-rejected route cannot suppress a later valid route. A later successful route preserves the first concrete witness, unions only newly learned contributor handles, and propagates them through the graph; it performs no new PM request, duplicates no activation, and re-evaluates no predicate. Since a node is revisited only when its finite contributor set grows, cycles still terminate.
5. Facet extraction then walks the active set. Sync's resolved skill pass evaluates each group and skill gate once while carrying the selected plugin route; ordinary callers use the boolean `collect_skills` adapter. Both use the same `load_skills_for_group` pipeline — honoring named groups, group predicates, and `source.path`/`source.git`, with each discovered skill's origin hashed from its on-disk `SKILL.md` path (this is where git skill sources are fetched, hence the `update` level). Duplicate install routes keep the first concrete witness but union their exact package contributors. MCP filtering consumes the already-active set and evaluates only each server's nested predicate after re-stamping its plugin's workspace provenance. Hook dispatch and subcommand lookup stay on the ordinary active set. A crate plugin's **custom predicate definitions** are the one facet still not wired in — they resolve only from configured registries, and `warn_undispatched_crate_features` notes when a crate declares one.

Skill discovery keeps the lexical bundle path used for installation while reading and hashing the final canonical `SKILL.md`. A path-sourced skill inherits package authority only when that final file remains inside the admitted package root. Escaped paths and detached Git groups remain usable, but cannot borrow the parent package's public naming authority.

A skill's install identity is the hash of its on-disk `SKILL.md` path, so a crate reached two ways dedupes to one install. The edge's version requirement is recorded but not yet enforced — the crate resolves against the workspace (pin / path override).

The key code paths are in `symposium-pm-cargo` (`CargoPm::load_plugin`, `plugin_from_fetched`, `manifest::merge`), `pm/mod.rs` (`PmInstance`, `AdmittedDependencies`, `PluginKind`), `plugins/agent_plugin.rs` (`agent_plugin_manifest`, `fill_from_agent_plugin`), `plugins.rs` (`validate_plugin`, `withheld`, `active_plugins_with`, `Plugin::canonical`), `audits/mod.rs` (`AuditIndex::revocation`), `skills.rs` (`resolve_skills`, `collect_skills`, `hash_origin_key`), `sync.rs` (`resolve_sync`), `telemetry/resolution_witness.rs`, and, in `symposium-pm-cargo`, `metadata.rs` (`symposium_metadata`), `workspace.rs` (`WorkspaceDeps`, `WorkspaceCrate`), and `sources.rs` (`RustCrateFetch`).

## Dependency enablement

A dependency's own plugin content (a `Symposium.toml`, `[package.metadata.symposium]`, an Agent Plugins `plugin.json`, or a `skills/` directory) is reachable without any manifest pointing at it, but only with the user's consent: dependencies are not a trust root.

1. `discovery::discover` asks the **untrusted** ecosystem transports for plugins embedded in the workspace's dependencies. Core transactionally admits each supplier's complete dependency listing, then projects each exact selected `PackageResolution` back to its supplier; predicates still consume only `PackageId`. Cargo inspects the source already extracted by metadata, with no probe or network. The trusted registries are skipped because they are trust roots. Each candidate is classified against `[plugins]` and the [audits list](../reference/audits.md): declined, revoked, enabled by `use`, auto-enabled, or undecided. Revoked offers are excluded from the consent prompt and session hint. Nothing is prompted or written.
2. At sync time, `discovery::enabled_admitted_dependencies` selects from the same owning `AdmittedDependencies` collection used by its resolved predicate context and gives every selected dependency's exact handle to the fixed point. Distinct packages sharing a coordinate remain distinct. A `use`d package outside the dependency snapshot contributes an unresolved coordinate instead. This still lets `cargo agents use <crate>` load a crate the workspace does not depend on. Bare names resolve through `discovery::Names`: a registry plugin first, then a dependency, then a package found by an ecosystem manager. `sync` resolves at `Check`; per-invocation paths use `None`. Matches from two managers remain ambiguous and enable nothing.
3. Independently, a registry plugin with no dependency gate anywhere loads *dormant* (`PluginManifest::requires_use`) and activates only when a `use` entry names it. The gate rides the `PredicateContext` (`with_used` / `is_used`), so skill resolution, hook dispatch, subcommand lookup, help, and MCP filtering all agree.

Decisions are recorded by the consent prompt in an interactive `cargo agents sync` (`discovery::prompt_for_consent`, which writes `auto-enable` and `disable`) and by `cargo agents use` (`use` entries); `cargo agents status` reports what `[plugins]` currently decides. A hook never prompts: `SessionStart` names the pending candidates as context instead. The prompt, the hint and `status` each show a candidate's audit answer (looked up once, cache-only, during discovery); it informs the decision and changes nothing about it.

The key code paths are in `discovery.rs`, `config.rs` (`PluginsConfig`, `UseEntry`), `symposium-pm-cargo` (`CargoPm::active_plugins`, `CargoPm::load_plugin`), `plugins.rs` (`PluginManifest::requires_use`, `active_plugins_with`), and `predicate.rs` (`PredicateContext::is_used`); bare names resolve in `discovery.rs` (`Names`, `used`).

## Help rendering

`cargo agents --help` (and `-h`, the bare `help` keyword, or no subcommand) is rendered by `help_render`, not by clap's default help.

1. The binary and the test harness parse argv with `Cli::try_parse_from`, then call `help_render::help_text(parse, args, sym, cwd)`. Because the decision happens after parsing, argument order (`--help --quiet`) does not matter and there is no second argv parser to keep in sync.
2. For no subcommand, `--help`/`-h`, or the bare `help` keyword, `help_text` returns the top-level grouped help: `render` slices clap's own rendered help (header + options block) and hand-renders "Commands for humans" / "Commands for agents" between them, mixing built-ins (`cli::builtin_audience`) with workspace-filtered plugin subcommands (`subcommand_dispatch::applicable_subcommands`).
3. For `<built-in> --help`, `help_text` re-renders clap's per-command help by walking clap's command tree to the named subcommand — so required-arg commands (`crate-info`), required-subcommand groups (`plugin`), and nested commands (`plugin list`) all work even though clap's auto help flag is disabled.
4. A plugin-vended `<name> --help` is left alone: `help_text` returns `None`, and dispatch forwards `--help` to the child binary, which owns its own help.

clap's auto help flag and help subcommand are disabled in `cli::Cli`; `--help`/`-h` is a manual `global` bool. The key code paths are in `help_render.rs` (`help_text`, `render`, `subcommand_help`), `cli.rs` (`builtin_audience`, the `Cli` flags), and `bin/cargo-agents.rs` plus `symposium-testlib` (the parse-then-`help_text` wiring).

## Subcommand dispatch

When the user runs `cargo agents <name>` for a name not built into the binary, clap's `allow_external_subcommands` routes it to `Commands::External(argv)`.

1. The binary (or library `cli::run`) calls `subcommand_dispatch::dispatch_external(sym, cwd, argv)`, which first resolves the **active plugin set** (`plugins::active_plugins` — registry plugins plus crate-sourced ones) so a crate's subcommands are dispatchable too.
2. `find_subcommand` walks that set. For each plugin it applies the plugin-level `depends-on` predicate against the workspace, then looks up `argv[0]` in `plugin.subcommands`. If the entry has its own `depends-on` predicate, that must also match. Two or more matches → error.
3. The matched subcommand's `command` field names an `Installation` on the same plugin. `installation::resolve_runnable` acquires the source if any, runs `install_commands`, and picks the `Runnable` (`Exec` for binaries, `Script` for shell scripts).
4. The child is spawned with stdio inherited. Its exit code is collapsed to a `u8` — the binary wraps it in `ExitCode::from`; the library treats non-zero as an error so the test harness can assert on success/failure.

The key code paths are in `subcommand_dispatch.rs`, `cli.rs` (the `External` arm), and `bin/cargo-agents.rs` (binary-side wrapping that surfaces the numeric exit code to the OS).

## Explicit plugin enablement

`cargo agents use` resolves registry plugins first, then workspace dependencies. For a name neither offers, it calls `PmInstance::find` on the ecosystem transports selected by `--pm`: a cached package is checked before search. As before, explicit `use` permits a search after a cache miss (`UpdateLevel::Check`), independently of the update level passed to the subsequent sync. Unselected transports are not queried in this fallback. The resolved canonical identity is recorded in `[plugins] use`.
